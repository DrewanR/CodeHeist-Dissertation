

For the programming elements of the game, a bespoke language called CatCode was created. This language would be designed to control entities in game, and was never intended to be fully featured. Early on, in requirement production period, it was decided that the editor, runner and output devices should be interchangeable to reduce coupling and increase flexibility. The relationships are shown in \autoref{fig:design/CatCodeBack/Overview}. This meant that CatCode could be initially developed as a text-based language with Graphical CatCode implemented at a later date. This also meant that CatCode could control entities other than \textit{CatBot}.

This system ended up far more complicated than anticipated and was largely responsible for the long Core System development time. A lot of the complexity was not originally anticipated, even with period dedicated to design, because many of the components, such as \textit{CatThreads}, had to be added due to unforeseen complications.

\subsection{Components}

As shown in \autoref{fig:design/CatCodeBack/Overview}, there are multiple main components, whose responsibilities are listed in \autoref{tab:design/CatCode/ComponentResponsibilities}. The centre, and manager of this system is the \textit{CatCodeManager} (sometimes semantically the \textit{CodeManager}, \texttt{res://src/catCode/cat\_code\_ manager.tscn}). This is instanced as a child of the node it is controlling. It stores the InstructionSet, a pair of variables: \texttt{instruction\_list} (a list of references instruction blocks) and \texttt{instruction\_dict} (a dictionary of the same references). By default, the \textit{LogicBlock} nodes are instanced as shildren of the \textit{CodeManager} node. Refer to \autoref{fig:catCodeSpec/files} for the file locations.

\subsection{The Logic Block Family of Classes}

The \texttt{logic\_block} family of classes, sometimes semantically called \textit{LogicalBlocks}, handle the back-end functionality of the blocks. These store the metadata and implementation of the function that of CatCode blocks. There are multiple different types of blocks, explained below and in the class diagram in \autoref{fig:design/CatCode/LogicBlockClassDiagram}. Godot does not have interfaces, instead abstract classes had to be used, nor does it support multiple inheritance, which greatly influenced this class structure.

    \caption{Partial class diagram of the LogicBlock family of classes}
    \label{fig:design/CatCode/LogicBlockClassDiagram}

The \texttt{logicBlock} directory is separated into two folders: \texttt{nodes} and \texttt{scripts}, with the superclasses getting stored in \texttt{classes}, refer to \autoref{fig:catCodeSpec/files} to more detail on the locations. This was to aid with dragging and dropping nodes in the editor to add blocks to the instruction set as accidentally dropping a script file onto the \textit{CodeManager} rather than the node will override the \textit{CodeManager}'s script.

Whilst many nodes have their own final script, this is not required as most of the metadata for each block is stored using \texttt{@export} variables (which can be set for each node in the editor). The purpose of each superclass is available in TAB. \autoref{app:supp} contains the \nameref{app:supp} which details each of the blocks in full.

The instruction set, for the level designer, is defined by dragging and dropping \textit{LogicBlock} nodes from the exploring onto the \textit{codeManager} node. Example shown in \autoref{fig:design/CatCode/ExampleCodeManagerInstance}. Certain nodes may require configuration within the inspector. When the \textit{codeManager} is instantiated, the \texttt{update\_instructions()} is called which creates the \texttt{instruction\_list} and \texttt{instruction\_dict}.

The \texttt{update\_instructions()} function does the following:

\begin{enumerate}
    \item Adds references to each of the child nodes from \texttt{instruction\_source} that are logic blocks to the list \texttt{instruction\_list}.\footnote{These nodes are identified through name (due to the lack of applicable universal \texttt{type()} method), taking advantage of the the naming scheme, \texttt{logicalBlock\_<type>\_<name>}, for logic blocks.}
    
    \item Iterates across this list, adding each block to the dictionary \texttt{instruction\_dict} where the key is the block's \texttt{block\_ref} and the value is a reference to the block.

    \item Emits the signal \texttt{instructions\_updated(new\_list :Array[logic\_block], new\_dict :Dictionary[String, logic\_block])}, to allow any relevant nodes to receive this new instruction set.
\end{enumerate}

\subsection{Compiled CatCode}

CatCode is compiled language. This is because, in many scenarios, a script is getting executed every frame meaning that execution speed is worth the cost in memory intensity. Because it is executed every frame, executions will greatly outnumber compilations. Also, relying on compiled CatCode for execution allowed the Code Editor to be swapped. It is the responsibility of the Code Editor to compile CatCode.

Compiled CatCode consists of an array of \texttt{instruction\_line} class instances (full definition available in \autoref{fig:design/CatCodeBack/instructionLineFull}). Each element represents a single line storing -- through \texttt{instruction\_line} -- a line's indent, a reference to the line's \textit{LogicBlock}, and its parameters. For interpretation to work as intended, the final block must be a \textit{pass} block where it's \texttt{indent} is \texttt{0}.

\subsection{Interpreting Compiled Code}

Compiled CatCode is interpreted sequentially by the runner (typically a \textit{CatThread}) using the \texttt{execute()} method in \texttt{cat\_thread.gd}. This is done by iterating across every index of the \texttt{compiled\_code}. The behaviour of this is modified by \texttt{indent\_stack}, a stack\footnote{Godot does not have a defined stack class. Instead, implements methods associated with stacks within the list data-type. However, for our algorithm this variable is always interacted with as a stack.} of \texttt{state\_stack\_layer} (class definition in \autoref{fig:design/catCode-stateStackLayer}), which manages structural elements such as \texttt{if} and \texttt{repeat}. The use of this stack allows for the interpretation of nested iteration, nested selection and any combination there of.

The indent stack is analogous to a call stack in many programming languages, where the top represents the current section of code. The most important element of this for sequential interpretation is \texttt{state} an enum that determines whether the current line of code should be executed (\texttt{PASS\_STATES.DO}) or skipped (\texttt{PASS\_STATES.SKIP} or \texttt{PASS\_STATES.SKIP\_ALL}).

To execute a function (provided all the conditions for its execution are met) \texttt{line.primary\_block.execute()} is called. If there are parameters, \texttt{.execute(line.params)} is called instead. Parameters are stored in an array to provide a standardized header for this functions regardless of parameter count.

\paragraph{Conditional Structures (\texttt{if}, \texttt{elif}, \texttt{else})}

As shown in \autoref{fig:design/CatCode-ConditionalFSM}, there are 5 states when interpreting conditional structures. Every state except the initial state \textquote{Evaluate} and the final state \texttt{end} are associated with the pass state of the same name.

In the evaluate state, the statement is evaluated. This is done the same way as functions are executed. When a statement is true it then goes to the \textquote{do} state. In this state all the blocks are executed (including nested structures). After this, if there are any \texttt{elif} or \texttt{else} blocks, it enters the \textquote{skip all} state where all lines are skipped until the end of this conditional structure. This to prevent unnecessary evaluations as only one section of a conditional structure can be executed.

When the previous statement is false, it enters the \textquote{skip} state. This will skip all lines until the next statement in the current conditional structure. If this statement is an \texttt{else}, than it enters the \textquote{do} state, else it will return to the \textquote{evaluate} state for the next statement.

There is no true \textquote{end} line, instead it will assume it is the end of a block when the indent of the next line is lower than the current stack it is not \texttt{elif} or \texttt{else}. If this is the case, the current top of the stack will be \textquote{popped} using the \texttt{pop\_back()} method. This is one of the cases where the \texttt{line\_number} is not incremented in case as this process needs to be repeated for every indent until the indent is once more where it is meant to be.

\paragraph{Iterative Structures (\texttt{repeat}, \texttt{forever})}

Similar to selective statements, when a iterative statement is reached a new \texttt{state\_stack\_layer} is pushed to the \texttt{indent\_stack}, the main purpose of this layer is to store the entry line and number of repetitions. When this occurs the current line number (\texttt{line\_number}) is not incremented. This is because so the statement is evaluated on the first iteration.

When the current line is the current iterative statement, it is evaluated using \texttt{line.primary\_block.evaluate([line.parameters[0], indent\_stack.back()])}. If it returns true, it remains in a \textquote{pass} state; else, it enters the \texttt{skip all} state.

When the end of the code section is reached (similar to conditional structures), if its in the pass state, the repetition count is increased and \texttt{line\_count} is set to the line of the current iterative statement; else, this structure will end similar to conditional structures. If the logic block for the statement returns \texttt{true} when \texttt{should\_wait\_for\_next\_frame()} is called, the runner will wait for the next frame before continuing.

\subsection{Multi-Threading and Run Options}

As a result of \texttt{repeat} blocks waiting for new frames for each iteration, there needed to be a method of handling clashing processes. This was done using \textit{catThread}s. These are instanced as children of the \textit{catCodeManager} and managed by it, referenced through the list \texttt{cat\_threads} and passed compiled catCode. The parameters that determine how theses threads are managed are shown in \autoref{tab:design/CatCode-threadParams}, as well as \autoref{fig:design/catBot-example-instance}b.
