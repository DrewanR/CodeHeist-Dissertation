
The character controlled by the player is \textit{CatBot}: a robot that looks like the cat, that has a failing control system that constants needs fixing. A cat was chosen as a combination for a few reasons. First, the developer is good at, and enjoys, drawing cats. Second, cats are popular companions with an estimated 10.2 million pet cats in the UK \citep{CatOwnership}. And, finally, but more importantly, the developer had an existing sprite-sheet, shown in  that could be re-used, alongside an existing system that could be used as a base.

\textit{CatBot} (found in \texttt{res://src/entities/player/player\_cat.tcsn}), which extends the custom-made \texttt{generic\_entity} class (...\texttt{/classes/generic\_entity.gd}). \texttt{generic\_entity} provides basic functions such managing HP, stability, and typing\footnote{Godot default type methods only provide the node type. This provides numerous functions, such as \texttt{move\_and\_slide()}, and attributes such as \texttt{velocity}.

\subsection{Mechanics}\label{sec:design/CatBot/ability}

\paragraph{Horizontal Movement}

Horizontal movement is handelled by adding \texttt{SPEED * direction * delta} to \texttt{velocity.x}, where \texttt{delta} is the time since last frame, \texttt{direction} is the horizontal input where 1 is right, and -1 is left, and \texttt{SPEED} is a constant determined through two other constants \texttt{MAX\_SPEED} and \texttt{SLIPMOD} (which controls \textquote{slippiness})

\begin{figure}
    \begin{fullwidth}
    \begin{tcolorbox}[boxrule=0.25mm]
    \begin{verbatim}
const SLIPMOD := 3.0
const MAX_SPEED := 160.0
...
const FRICTION_CONST := 0.15/SLIPMOD
...
## Handles horizontal physics
func horizontal_physics(_delta: float, direction: float) -> void:
    var slipmod_adjustment := 1.0 if abs(direction) > 0 else SLIPMOD*0.75
    velocity.x = lerp(velocity.x, 0.0, FRICTION_CONST * slipmod_adjustment)
    \end{verbatim}
    \end{tcolorbox}
    \end{fullwidth}
    \caption{Horizontal physics function}
    \label{fig:design/catBot-HorPhys}
\end{figure}

Friction is more complex, using the \texttt{lerp()} function to allow for a non-linear regression in momentum whilst remaining consistent at different frame-rates. The constant \texttt{FRICTION\_CONST} is used to determine the strength of the friction, as well as \texttt{SLIPMOD} when not running. This is handled by the function in \autoref{fig:design/catBot-HorPhys}.

\paragraph{Vertical Physics and Jumping}

Every frame \texttt{is\_on\_floor()} is false (meaning CatBot is in the air), the global gravity value (gotten using the method \texttt{get\_gravity()}) is \textit{added} to \texttt{velocity.y}\footnote{The y-axis is inverted in Godot's 2D engine.}. When this is true, \texttt{air\_time()} is increased by \texttt{delta}.

To jump, we set \texttt{velocity.y} to \texttt{JUMP\_VELOCITY} if grounded. For the purposes of jumping, to improve the feel of movement, we have implemented Coyote-time inspired by Celeste \citep{Celeste} \citep{GameRant-CoyoteTime}. This changed the condition to jump from \texttt{is\_on\_floor()} to \texttt{air\_time < COYOTE\_TIME}.

\paragraph{Swiping}

This was added as a secondary action. When CatBot swipes -- endlessly whilst grounded, or up to \texttt{MAX\_AIR\_STRIKES} (2) in mid-air -- it gains a small impulse of velocity and spawns an attack node (implementation of this part is not relevant to this report). The pseudocode is shown in \autoref{fig:design/catBot-swipeFun}.

\begin{figure}
    \begin{tcolorbox}[boxrule=0.25mm]
    \begin{verbatim}
FUNC strike(direction):
    IF (Cannot_strike):
        Throw error
    ELSE:
        air_strikes ← air_strikes + 1
        strike_cooldown ← STRIKE_COOLDOWN_COST

        IF is_on_floor():
            velocity ← STRIKE_VELOCITY * Vector2(
                direction, 1 + get_direction_y()
            )
            air_entry ← 6
            air_time ← 0
        ELSE:
            velocity = STRIKE_VELOCITY * Vector2(
                direction*1.25, 1 + get_direction_y() * 0.75
            )
        ENDIF
        add_attachment(strike_attachment_node)
    ENDIF
ENDFUNC
    \end{verbatim}
    \end{tcolorbox}
    \caption{Swipe function (pseudocode)}
    \label{fig:design/catBot-swipeFun}
\end{figure}

\subsection{Traditional Systems}\label{sec:design/CatBot/traditional}

The original physics system was inspired by a previous system by the developer with some mechanics removed such as climbing, and then adapted. The structure and the constants\footnote{Hence why there are a few unused constants in case mechanics, such as climbing, were re-implemented later} were what remained. This system, as is typical for Godot, makes use of the \texttt{\_ready()} and \texttt{\_physics\_process(delta)} (which is similar to \texttt{\_process(delta)}).

The \texttt{\_physics\_process()} function, which handles all the logic, does the following in order:

\begin{enumerate}
    \item[1.] Vertical logic
        \subitem 1.1. Handles vertical calculations
        \subitem 1.2. Handles jump logic
    \item[2.] Horizontal logic
        \subitem 2.1. Handles friction calculations
        \subitem 2.2. Handles walking logic
    \item[3.] Handles any other actions
    \item[4.] Moves the node
    \item[5.] Handles animations
\end{enumerate}

A flow chart showing this process is available in \autoref{fig:design/catBot-TraditionalFlow}, as well as the function itself in \autoref{fig:design/catBot-TraditionalProcFun}. This order of operations was maintained throughout.

\begin{figure}[H]
    \centering
    \includegraphics[width=1\linewidth]{C5//CatBot/playerCatStage1_flowDiagram.png}
    \caption{Flow chart showing the logic for a traditional platformer character}
    \label{fig:design/catBot-TraditionalFlow}
\end{figure}

\begin{figure}
    \begin{tcolorbox}[boxrule=0.25mm]
    \begin{verbatim}
func _physics_process(delta: float) -> void:
    var direction := get_direction_x()
    debug_text = ""
    animation_state = 0
    
    # Air physics
    calculate_airtime(delta)
    vertical_physics(delta)
    
    # Handle jump
    calculate_walktime(delta, direction)
    jump_logic(delta)
    
    # Ground physics
    running_logic(delta, direction)
    horizontal_physics(delta, direction)
    
    # Other
    strikes(delta, direction)
    
    previous_velocity = velocity
    facing_right = velocity.x >= 0
    move_and_slide()
    
    # Animations
    flip_sprite(direction, false)
    calculation_animation_state(direction, delta)
    animation()
    update_debug_text()
    
    # Sets velocity.x to 0 if it is low enough
    velocity.x *= 1 if (abs(velocity.x) >= delta*5) else 0
    
    # Debug
    if Input.is_action_just_pressed("debug_damage"):
        damage(1)
    if Input.is_action_just_pressed("debug_heal"):
        heal(1)
    \end{verbatim}
    \end{tcolorbox}

\subsection{Extracting the Controllers}\label{sec:design/CatBot/modularisation}

After the traditional player character was created, the control systems were removed from the node. This was when the player character became \textit{CatBot}. In this process, nodes were created that can be instanced as children which would execute the actions instead of the \textit{CatBot} node itself, an example of this node setup is in \autoref{fig:design/catBot-ModularisedNodes}.

Lets use the jumping as an example. Jumping was originally handled in its entirety by the \texttt{jump\_logic()} function. First, this was split into \texttt{jump(strength)}, which executed the jump and \texttt{jump\_logic()}, which would execute the \texttt{jump()} when appropriate. Then, \texttt{jump\_logic()} was moved over to the node \textit{AutoJumpController} (\texttt{res://src/entities/player/autoControllers}), which would call the \texttt{jump()} function on its parent. Pseudocode for this process is shown in \autoref{fig:design/catBot-ModularisedFun}. \subsection{Adding CatCode to CatBot}\label{sec:design/CatBot/instancing}

CatCode was initially created in isolation, with this integration with \textit{CatBot} in mind. As is standard with CatCode, a \textit{CodeManager} is added as a child to the \textit{CatBot} node. This \textit{CodeManager} will then execute functions on its parent as appropriate (shown in). No modifications were needed to \textit{CatBot} as, from its perspective, a \textit{CodeManager} is indistinguishable from an \textit{autoController}.
